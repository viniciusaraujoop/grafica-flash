## Production Storage RLS

Authenticated direct Storage policies cover `financeiro`, `logos`, `product-images`, `produtos`, `site-assets` and require `orcaly_private.can_manage_storage_path(name)` for SELECT/INSERT/UPDATE/DELETE.

This makes the company path an authorization boundary. The path generated by the panel uploader begins with the validated company UUID.

`artes` is outside those authenticated policies and is written by the server/service-role public upload route.

## Audited upload paths

### `POST /api/site/upload`

Controls:
- authenticated requester;
- company access and `canManage`;
- same-origin;
- DB-backed rate limit: 30 / 10 minutes per requester;
- 10 MiB cap;
- JPEG/PNG/WEBP/GIF allowlist;
- magic-byte validation;
- WEBP RIFF + WEBP marker check;
- SVG excluded;
- filename/purpose sanitization;
- company-ID path prefix;
- random component;
- `upsert:false`;
- public URL returned.

Status: **PASS for this route**.

Residual:
- it calls `createBucket` defensively with service role. Live bucket already exists; this is operationally unnecessary but not a demonstrated exploit.
- malware scanning is not configured.

### `POST /api/public/uploads/art`

Controls:
- same-origin;
- DB-backed rate limit: 5 / 10 minutes;
- early content-length bound;
- 10 MiB file cap;
- JPEG/PNG/WEBP/PDF allowlist;
- magic bytes;
- server-generated UUID path;
- active company slug resolution;
- `upsert:false`.

Status: **PARTIAL**.

Residual:
- an anonymous same-origin caller that knows an active company slug can place a valid allowed file in that company's public `artes` namespace. Rate limiting reduces abuse but there is no signed quote/order/upload-intent capability binding the upload to a specific workflow.
- because the bucket is public, possession of the object URL is sufficient for read access.

Recommended: P2 capability-bound upload intent if/when the quote/art workflow is revisited. No runtime change is justified in this final docs-only checkpoint.

### Client panel uploader: `lib/panel-storage.ts`

Controls:
- validates company UUID;
- company UUID prefixes object path;
- random file component;
- size limits per purpose;
- `upsert:false`;
- private finance files use storage references, not public URLs;
- private URL resolution defaults to a 300-second signed URL.

Gaps:
- client-side MIME/extension validation is not a content-signature validator;
- logo accepts `image/svg+xml`;
- product-image accepts any `image/*` MIME before extension fallback, so active formats can pass MIME-prefix validation;
- product/video public buckets do not have bucket-level MIME allowlists;
- finance PDF/XML has no magic-byte/content parser validation in this client path.

Classification: **PARTIAL / P2 hardening**. RLS prevents cross-company direct writes; content validation is the remaining concern.

## Wealth Documents

Positive evidence:
- private `wealth-documents` bucket;
- 3 MiB limit;
- PDF/JPEG/PNG only;
- bytes determine MIME;
- mismatched declared MIME is rejected;
- SHA-256 + size persisted and rechecked on download;
- object path is `<user id>/<document id>/document`;
- authenticated owner/entitlement gate;
- upload is reserved/finalized through RPC;
- `upsert:false`;
- two-phase deletion closes logical access before object removal;
- download route uses `private, no-store`, `nosniff`, restrictive CSP sandbox and attachment disposition;
- access is rechecked after object retrieval;
- family sharing rechecks share authorization after retrieval;
- certified E2E asserts cross-user denial;
- E2E explicitly asserts signed URL creation is denied for the private Wealth object.

Status: **PASS for the certified Wealth Documents scope**.

## Signed URLs

Known use:
- private Business finance references: `resolvePanelStorageUrl(..., expiresIn=300)` defaults to five minutes.
- Wealth Documents intentionally streams through authenticated server routes rather than exposing signed URLs; E2E expects direct signed URL creation to fail.

Global signed-URL inventory outside these paths was not proven exhaustive by this document.

## Filename / path traversal

Positive:
- server site upload sanitizes filename/purpose;
- public art uses UUID filename;
- panel uploader validates company UUID and normalizes filename;
- Wealth uses server-generated UUID segments.

No direct `../` path construction was found in these audited paths.

## Executable / active content

- audited site server upload excludes SVG and executable formats.
- public art supports PDF. It is public content; browsers should serve correct content type and users should not be induced to treat arbitrary public artwork as trusted application HTML.
- panel logo currently allows SVG.
- product media client accepts broad image/video MIME classes.
- no HTML/JS upload purpose is intentionally allowed.

Recommendation: tighten active/public formats in a later owner-approved hardening pass, especially SVG, and add server-side magic/parser validation for legacy client uploads.

## Malware scanning

**NOT_CONFIGURED / not found** for these upload paths.

Magic-byte validation proves container type, not malware safety. Wealth source code explicitly documents that distinction.

A malware scanner is operationally valuable for untrusted PDFs/documents but should be added as a provider/queue design with quarantine semantics, not improvised inline during Phase A.

## Cleanup / deletion

- Wealth: strong two-phase delete + E2E cleanup evidence.
- panel/public site/art media: no repository-wide orphan cleanup certification was established here.
- public object retention policy is not documented as a security control.

Classification: operational P3 gap.

## Service-role use

Service role is used in the audited server upload routes only after application authorization/validation. Direct browser upload relies on Storage RLS rather than embedding service credentials.

No client component source reference to `SUPABASE_SERVICE_ROLE_KEY` was found by the Phase A secret inventory.

## Result

**UPLOAD / STORAGE: PARTIAL overall.**

Strongest path: Wealth Documents.  
Strong server path: `/api/site/upload`.  
Open hardening: public-art capability binding, legacy client magic-byte/active-format validation, malware scanning and retention/cleanup policy.
